# Design
## Context
See proposal.md, Why, for the problem. These facts shape the approach:
1. [ELV-002] derives each element-type name from a canonical type name, and [MDL-009] makes the naming manifest the
   source of each canonical type name. A union branch is an entry of kind `object` ([NAM-010]).
2. [ELV-001] validates an element value against the constraints of the named type. The text does not limit the value
   to a JSON object.
3. The `validate-element` check of `scripts/check-corpus.ts` finds an element type by the local name of a schema
   definition, not by the list of [ELV-002.01]. 19 such local names, for example `with-id`, are not in the list.
4. The corpus has no case that compares the list of [ELV-002.01]. Each case in `corpus/1.2.3/cases.json` has an
   `input`, and `scripts/check-corpus.ts` fails a case whose input does not exist. The files under `expected/` are
   generated by `npm run corpus:write`.
5. The 244 canonical names of OSCAL 1.2.3 give 244 different kebab-case names. Code-point order and the `en` locale
   order of `Intl.Collator` give the same sequence for them. The TypeScript list is in code-point order.
6. [ELV-002] has 494 characters with this change. OpenSpec limits the text of a requirement to 500 characters.
## Goals / Non-Goals
**Goals:**
1. One list of element-type names for each binding of OSCAL 1.2.3.
2. A corpus case that fails a binding whose list is different.
**Non-Goals:**
1. A change to a binding. Each binding changes when it moves its pin.
2. A change to the cases of `validate-element`.
## Decisions
### D1. Each kind of manifest type has an element-type name
[ELV-002] already derives the names from the canonical type names and excludes no kind. The change states that
reading.
1. **Alternative considered: the set of the Python binding.** It leaves out unions but keeps their branches. A caller
   can then validate `parameter-with-select` but not `parameter`. No rule of the specs gives that set. Rejected.
2. **Alternative considered: all kinds except `enum`.** An enum value is a string, not an object. But [ELV-001] does
   not limit an element to an object, and an exception adds a rule that no problem needs. Rejected.
### D2. A corpus case checks the list
The new operation `element-types` requests the supported element types. The case passes when the list of the binding
equals the list in `expected/element-types.json`, item by item and in the same order.
1. **Why a generated file:** the runner of each binding compares two lists and does not derive kebab-case names
   itself. The store generates the file, and `npm run corpus:check` fails when the file is not the list that the
   manifest gives.
2. **Alternative considered: a list in `manifest/1.2.3/`.** No corpus runner reads it, so no binding test would use it
   without new work in each binding. Rejected.
3. **Alternative considered: one `validate-element` case for each kind.** That tests that some names exist. It does
   not find an extra name such as `root-model`. Rejected.
### D3. The form of the case and of the expected file
1. The case has the fields `id`, `operation`, `expected`, and `requirements`. It has no `input`. The checker skips the
   input checks for the `element-types` operation.
2. The expected file is the canonical form of a JSON array of strings, as `docs/canonical-json.md` defines it.
3. The checker derives each name from the `name` of each entry in `types` of `manifest/1.2.3/names.json`. It puts a
   hyphen before each uppercase letter that follows a lowercase letter or a digit, and then makes each letter
   lowercase. So `BackMatterResourceBase64` gives `back-matter-resource-base64`, as in both bindings. The checker
   sorts the names in code-point order.
4. The checker fails when two manifest types give the same name. A binding could not then give one name to each type.
5. A `validate-element` case with `expected-valid` names an element type in the list. A case with the category
   `unknown-element-type` names an element type that is not in the list. The checker keeps its schema checks of these
   cases.
6. `npm run corpus:write` writes the file. `npm run corpus:check` fails when the file differs from the derived list,
   and when the case does not name the file.
### D4. `VERSION` stays `0.8.0+oscal.1.2.3`
The change is a break for a binding that leaves out a kind. Under the Semantic Versioning rule for `0.y.z` versions,
the store makes a break a minor increment. `VERSION` is `0.8.0+oscal.1.2.3`, the latest tag is `v0.7.0+oscal.1.2.3`,
and the change `clarify-manifest-consumer-rules` set `0.8.0` for its own break. So the next release already has a
minor increment.
## Risks / Trade-offs
1. [A binding runner fails on the unknown operation `element-types`] → Each binding adds the operation when it moves
   its pin. The pull request description and the binding issues of the workflow follow-up name the operation.
2. [The expected file repeats data of the manifest] → The file is generated, and the check fails when it differs.
